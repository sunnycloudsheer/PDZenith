- `RESCHEDULED_EMAIL_TEMPLATE_ID = '00Xbb000003UJbN'`

These are referenced 5+ times in the class (lines 348, 384, 1453, 1456, etc.).

### Why it matters
In Production, these Ids do not exist — the templates have different Ids in every org. Every email sent through `ZoomMeetingManager` would fail or pick up the wrong template.

### Depends on
Task #4 (production templates with stable DeveloperNames must exist).

### What I need from you
Confirm the three DeveloperNames Task #4 settled on. Default suggestion:
- `Zenith_Meeting_Scheduled`
- `Initial_Consultation_Meeting_Scheduled`
- `Meeting_Rescheduled_Email_Template`

### Implementation plan
1. Remove the three `private static final Id` constants.
2. Add a static helper:
   ```apex
   private static Map<String, Id> templateIdsByDevName;

   @TestVisible
   private static Map<String, Id> testOverride;

   private static Id getTemplateId(String devName) {
       if (testOverride != null) return testOverride.get(devName);
       if (templateIdsByDevName == null) {
           templateIdsByDevName = new Map<String, Id>();
           for (EmailTemplate t : [
               SELECT Id, DeveloperName FROM EmailTemplate
               WHERE DeveloperName IN (
                   'Zenith_Meeting_Scheduled',
                   'Initial_Consultation_Meeting_Scheduled',
                   'Meeting_Rescheduled_Email_Template'
               ) AND IsActive = true
           ]) {
               templateIdsByDevName.put(t.DeveloperName, t.Id);
           }
       }
       Id id = templateIdsByDevName.get(devName);
       if (id == null) {
           throw new IllegalStateException('EmailTemplate not found: ' + devName);
       }
       return id;
   }
   ```
3. Replace each reference, e.g.
   ```apex
   // BEFORE
   sin.templateId = SCHEDULED_EMAIL_TEMPLATE_ID;
   // AFTER
   sin.templateId = getTemplateId('Zenith_Meeting_Scheduled');
   ```
4. Update `ZoomMeetingManagerTest` to inject `testOverride` so tests don't depend on real EmailTemplate records.

### Files I will modify
- `force-app/main/default/classes/ZoomMeetingManager.cls`
- `force-app/main/default/classes/ZoomMeetingManagerTest.cls`

## Task #16 — Replace 51 empty `catch` blocks with logging

### Problem
The codebase has **51 silently-swallowed exceptions** distributed across 6 classes:

A typical block looks like `} catch (Exception e) { }` — the exception is caught and discarded.

- When users report "the link wasn't generated" or "the email never arrived", we have no way to diagnose without re-running with manual logging.

### Why this is "best-effort guard" vs "anti-pattern"
**Some** of these are intentional: code that tries to set an optional field which may not exist on every customer's org (e.g. `try { sa.put('CancellationReason', ...) } catch (Exception e) { }`). For these, swallowing is correct — we just need observability.

### Depends on
Nothing.

### What I need from you
1. **Logging policy** — pick one:
   - **(A)** Just add `System.debug(LoggingLevel.WARN, ...)` to every empty catch. Lowest risk, no schema change.
   - **(B)** Write to a custom `Error_Log__c` object so failures are visible without enabling debug logs. Requires creating that object first.
   - **(C)** Mix: option (A) for "best-effort guards", option (B) for genuine errors.

   Default recommendation: **(A)** for v14, plan **(C)** for a later release.

### Implementation plan (assuming option A)
For each empty catch, replace:

```apex
// BEFORE
} catch (Exception e) { }

// AFTER
} catch (Exception e) {
    System.debug(LoggingLevel.WARN,
        '<MethodName> [<context>]: ' + e.getMessage());
}
```

I'll choose appropriate context strings per location (method name + the variable being touched).

## Task #18 — Add `WITH USER_MODE` to LWC-backing controller queries

### Problem
`LeadFamilyController.cls` and `OpportunityPipelineController.cls` are `with sharing` Aura controllers, but their SOQL queries do not use `WITH USER_MODE`. This means even though the class respects sharing, the **field-level security** of the queried fields is not enforced at the query layer.

### Why it matters
- If a user lacks read on `Lead.No_of_Student_Enrolling_Today__c`, the query still returns it — only the LWC layer filters it. Cleaner to enforce at the query.
- `WITH USER_MODE` is the modern, recommended replacement for `WITH SECURITY_ENFORCED` (Apex API 60+).
- It surfaces FLS issues as `QueryException` instead of silent data exposure.

### Depends on
Nothing.

### What I need from you
Nothing — this is a hygiene change.

### Implementation plan
For every `[SELECT ...]` literal in both files, append `WITH USER_MODE` before the closing bracket:

```apex
// BEFORE
List<Lead> leads = [SELECT Id, FirstName FROM Lead WHERE Id = :leadId];

// AFTER
List<Lead> leads = [SELECT Id, FirstName FROM Lead WHERE Id = :leadId WITH USER_MODE];
```

DML in those classes should also be flipped to user-mode form (`Database.update(records, AccessLevel.USER_MODE)`).

### Files I will modify
- `force-app/main/default/classes/LeadFamilyController.cls`
- `force-app/main/default/classes/OpportunityPipelineController.cls`

### Verification
- All queries have `WITH USER_MODE`.
- Existing tests pass for an admin user.
- Manual test as a non-admin user (with full FLS) still works.
- Manual test: temporarily remove FLS on one queried field → controller throws `QueryException` (expected and good).

### Suggested commit message
